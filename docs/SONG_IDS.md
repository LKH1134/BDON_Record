# Songs 인덱스와 곡 분류

2026-10-28 `test` 브랜치에서 개발·검증하고 `main` 병합·Workers 운영 배포·D1 기록 이전을 완료했습니다. 운영은 6자리 곡 ID와 93곡 카탈로그를 사용합니다. 기존 ID(`1001`~`1092`)는 이전 대응표에만 보관합니다.

## ID 구조

곡 ID는 `밴드 코드 2자리 + 곡 분류 1자리 + 분류별 순번 3자리`의 6자리 정수입니다. 예를 들어 `102007`은 MyGO!!!!!(`10`)의 커버(`2`) 7번째 곡(`007`)입니다.

- `xx1xxx`: 오리지널
- `xx2xxx`: 커버
- 순번은 밴드·분류별로 `001`부터 시작합니다. 새 곡은 해당 그룹의 마지막 순번 다음에 추가하며 기존 ID를 다시 매기거나 재사용하지 않습니다.
- 기타 밴드는 코드 `60`을 사용하고 실제 밴드명은 보존합니다. 현재 CRYCHIC의 `601001`은 오리지널입니다.

| 밴드 | 오리지널 ID | 커버 ID |
| --- | --- | --- |
| MyGO!!!!! (`10`) | 101001~101018 | 102001~102007 |
| Ave Mujica (`20`) | 201001~201018 | 202001~202007 |
| 무겐다이 뮤타입 (`30`) | 301001~301017 | 302001~302005 |
| millsage (`40`) | 401001~401005 | 402001~402005 |
| 일가 Dumb Rock! (`50`) | 501001~501005 | 502001~502005 |
| 기타 (`60`, 실제 밴드 CRYCHIC) | 601001 | 없음 |

총 93곡이며 오리지널 64곡, 커버 29곡입니다. 원본 메모의 millsage·일가 커버 시작값 `401002`·`501002`는 오리지널 ID와 겹치므로 사용자 추가 지시의 `xx2xxx` 규칙에 맞춰 `402001`·`502001`로 적용했습니다. 「Abracadabra」는 `1091 → 202006`, 「논브레스 오블리주」는 `1092 → 102007`입니다. 이후 추가한 Ave Mujica 커버 「怪物 / KAIBUTSU」는 임시 ID `991001`을 `202007`로 변경했습니다. 임시 ID는 기록 이전 대응표에 추가하지 않습니다.

## 엑셀과 카탈로그

`Songs`의 열 순서는 다음과 같습니다. 행은 곡 ID 오름차순입니다.

| 열 | 헤더 | 의미 |
| --- | --- | --- |
| A | index | 6자리 곡 ID |
| B | 곡 이름 index | 기존 Strings ID 참조 |
| C | 밴드 | 실제 밴드명 |
| D | 곡 분류 | `오리지널` 또는 `커버` |
| E~H | Expert / Hard / Normal / Easy | 기존 레벨 |

`Strings`의 ID·원문·번역명·행 순서는 유지했습니다. `songs` JSON에는 `category`가 추가됩니다. 예:

```json
{
  "id": 102007,
  "nameId": 2092,
  "band": "MyGO!!!!!",
  "category": "커버",
  "levels": { "expert": 26, "hard": 20, "normal": 14, "easy": 7 }
}
```

`npm run sync-data`는 헤더, 6자리 ID, 순번 `001`~`999`, ID와 밴드·분류의 일치, 중복 ID, 문자열 참조와 레벨을 검증합니다. 분류를 자동 추측해 잘못된 입력을 덮어쓰지 않습니다. 화면의 별도 분류 표시·필터는 이번 작업에 포함하지 않았습니다.

`Info` 시트에 밴드 코드·분류 코드·순번 배정·Strings 참조 규칙과 현재 ID 범위·신곡 적용 예시를 정리했습니다. `991001`은 임시 인덱스 안내로 남기되 Songs의 실제 ID는 정식 코드로 변경합니다. importer는 `Songs`와 `Strings`만 읽으며 `Info`는 안내용입니다.

## 기존 기록 이전

`migrations/0002_song_ids.sql`에 92곡 전체의 이전 ID와 새 ID 대응표가 있습니다. Node SQLite와 D1에서 같은 SQL을 사용합니다. `records.song_id`만 단일 UPDATE로 변경하며 사용자·세션·난이도·상태·수정 시각은 보존합니다. 반복 실행 시 이전할 행이 없으면 변경하지 않으며, 대상 ID와 기본 키가 충돌하면 덮어쓰지 않고 전체 UPDATE가 실패합니다. 대응표에 없는 기록도 유지합니다.

### Node 로컬 DB

서버를 먼저 종료한 뒤 명시적인 DB 경로로 확인합니다. 기본 실행은 읽기 전용이고, `--apply`를 붙여야 실제 이전합니다.

```powershell
npm run migrate:song-ids -- --db .local/bdon.sqlite
npm run migrate:song-ids -- --db .local/bdon.sqlite --apply
```

실제 이전 전에 같은 위치에 `bdon.sqlite.before-song-ids-<시각>.sqlite` 백업을 만듭니다. 이전 실패 시 원본 기록은 유지되며 백업도 남습니다. 실제 사용자 DB를 이 개발 작업에서 실행·초기화·이전하지 않았습니다. Node 서버는 이전 ID 기록이 남아 있으면 실행을 중단하고 이전 명령을 안내합니다.

### Workers D1 공개 반영

개발 검증에는 임시 DB를 사용합니다. `test`에서 원격 migration이나 운영 배포 명령을 실행하지 않습니다.

공개 반영을 요청받으면 검증한 변경을 `main`에 병합합니다. `npm run deploy:worker -- --var RECORDS_MAINTENANCE:1`로 기록 조회·저장을 잠시 중단한 버전을 배포하고, D1 export 백업과 DB 대상·미적용 migration 목록을 확인합니다. 그 후 명시적으로 `npm run db:remote`로 `0002_song_ids.sql`을 적용해 기록 수·상태·시각·레이팅 보존을 비교하고 `npm run deploy:worker`로 점검 모드를 해제합니다. 기본 설정은 `RECORDS_MAINTENANCE=0`입니다. GitHub Pages도 새 카탈로그로 갱신합니다.

배포 전후에는 사용자별 기록 수·상태·수정 시각과 레이팅 합계, 로그인 유지, 신 ID의 조회·저장·해제, 372차트 일괄 저장을 확인합니다. 새 Worker는 이전 ID 기록이 남아 있는 동안 기록 조회·저장에 503을 반환해 기록이 없는 것처럼 표시하거나 새 ID 기록과 섞어 저장하는 것을 막습니다. 이전 화면을 열어 둔 사용자는 새로고침해야 합니다. 문제가 생기면 운영 편집을 중단한 상태에서 DB 복원과 이전 Worker 버전 복원을 함께 검토합니다.
